# Netpeak AI Solutions — тріаж інбоксу запитів

Сервіс читає `input_requests.csv` (запити від внутрішніх команд у вільній формі),
проганяє кожен запит через LLM, валідує вивід у строгу схему і формує
`output.json` + агрегований звіт.

> **Прогін у репозиторії зроблено на мок-провайдері** (`--provider mock`) — без
> ключа до API. Мок віддає заздалегідь підготовлені відповіді на ці 18 запитів,
> зокрема навмисно биті на першій спробі, щоб було видно роботу валідації та
> ремонту. Цифри в `out/report.md` — це якість фікстур, а не якість моделі.
>
> Провайдер `--provider gemini` **перевірено живими викликами** на всіх 18
> запитах (окрема сесія з ключем, детально — розділ
> [«Перевірка на живому Gemini»](#перевірка-на-живому-gemini)). Під час першої ж
> перевірки живі виклики знайшли два реальні дефекти в коді, яких мок пропустив
> — обидва виправлено, деталі там-таки.
>
> Три опціональні плюси — **Google Sheets, Telegram-дайджест і Docker** —
> написані з тестами на все, що перевіряється без зовнішніх сервісів, але жоден
> не прогнаний по-справжньому: немає під рукою ні service account, ні
> бот-токена, ні робочого Docker-демона в цій сесії. Детально й чесно — розділ
> [«Опціональні плюси»](#опціональні-плюси-google-sheets-telegram-docker).

## Запуск

Потрібен Python 3.11+.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m src.main --provider mock
```

Це створить `out/output.json`, `out/report.md`, `out/report.csv`.

Реальний прогін через Gemini (безкоштовного тіру вистачає):

```bash
cp .env.example .env   # і встав GEMINI_API_KEY
python -m src.main --provider gemini
```

Тести:

```bash
pip install -r requirements-dev.txt && pytest -q
```

Docker (Dockerfile написаний і пройдений вручну рядок за рядком, але жодного разу
не збирався — деталі й чому у розділі
[«Опціональні плюси»](#опціональні-плюси-google-sheets-telegram-docker) нижче):

```bash
docker build -t triage . && docker run --rm -v "$PWD/out:/app/out" triage
```

Опціональні плюси — запис у Google Sheet і дайджест у Telegram (теж ненульова
частина — деталі в тому ж розділі нижче):

```bash
pip install -r requirements-optional.txt
python -m src.main --provider gemini --write-sheet --telegram-digest
```

### Змінні оточення

| Змінна | Обовʼязкова | Призначення |
|---|---|---|
| `GEMINI_API_KEY` | тільки для `--provider gemini` | ключ з [aistudio.google.com/apikey](https://aistudio.google.com/apikey) |
| `GEMINI_MODEL` | ні | модель, за замовчуванням `gemini-3.6-flash` |
| `GOOGLE_SHEETS_SPREADSHEET_ID` | тільки для `--write-sheet` | ID таблиці з її URL |
| `GOOGLE_SHEETS_CREDENTIALS_FILE` | тільки для `--write-sheet` | шлях до JSON-ключа service account |
| `TELEGRAM_BOT_TOKEN` | тільки для `--telegram-digest` | токен від @BotFather |
| `TELEGRAM_CHAT_ID` | тільки для `--telegram-digest` | куди слати дайджест |

Ключі читаються з `.env` (він у `.gitignore`) або з оточення. У репозиторії лежить
тільки `.env.example` з покроковими коментарями, як отримати кожен з них.

### Прапорці

| Прапорець | Замовчування | Навіщо |
|---|---|---|
| `--provider` | `mock` | `mock` \| `gemini` |
| `--input` | `data/input_requests.csv` | інший вхідний файл |
| `--out-dir` | `out/` | куди писати результат |
| `--concurrency` | `5` | скільки запитів паралельно |
| `--repair-attempts` | `1` | скільки разів перепитати модель після помилки валідації |
| `--no-cache` | вимкнено | ігнорувати кеш відповідей |
| `--temperature` | `0.0` | температура моделі |
| `--write-sheet` | вимкнено | записати результат у Google Sheet (опціональний плюс) |
| `--telegram-digest` | вимкнено | надіслати дайджест у Telegram (опціональний плюс) |

Код повертає ненульовий exit code, якщо хоч один запит завершився статусом `failed`
— щоб це було видно в CI чи в cron. `--write-sheet`/`--telegram-digest` на це не
впливають: якщо потрібні змінні оточення не задані, прапорець просто пропускається
з попередженням у консоль, а не валить прогін, що вже успішно записав
`output.json`/`report.md`.

## Як влаштовано

```
src/
├── models.py        # pydantic-схеми — єдине джерело правди
├── prompt.py        # системний промпт + few-shot + версія промпту
├── llm/
│   ├── base.py      # вузький протокол провайдера
│   ├── gemini.py    # реальний провайдер (response_schema + backoff)
│   ├── mock.py      # детермінований провайдер на фікстурах
│   └── mock_fixtures.json
├── cache.py         # кеш відповідей на диску
├── pipeline.py      # async-обробка, валідація, ремонт
├── report.py        # агрегати (чистий Python, без LLM)
├── integrations/    # опціональні плюси, кожен ловить власні помилки
│   ├── sheets.py     # запис у Google Sheet (gspread)
│   └── telegram.py   # дайджест у Telegram (stdlib, без залежностей)
└── main.py          # CLI
```

Схема з `models.py` конвертується в JSON Schema і віддається моделі як
`response_schema` — форму гарантує сам декодер, а не парсер після факту. Pydantic
потім ловить те, що схемою не виражається: вигаданий відділ, суперечливу
комбінацію полів, порожній список дій.

Звіт рахується виключно по вже валідованих даних. Другого виклику LLM для
агрегації немає — інакше в цифрах теж зʼявився б недетермінізм.

## Розширення схеми і чому саме такі

Обовʼязковий мінімум із ТЗ на місці. Додано шість полів — кожне закриває
конкретний випадок із цього ж датасету, а не «про всяк випадок»:

| Поле | Навіщо |
|---|---|
| `clarifying_questions` | Без нього `needs_clarification: true` марний: PM усе одно йде читати оригінал. З ним рядок звіту вже готовий до відправки автору. |
| `priority_rationale` | `priority` виводиться «з тону» — найсубʼєктивніше поле. Вимога пояснити причину і дисциплінує модель, і робить помилку помітною при ревʼю. |
| `deadline_mentioned` | REQ-005 («сьогодні до вечора») і REQ-015 («до кінця місяця»). Зберігаємо дослівно, без парсингу в дату: «до кінця місяця» надійно не розпарсити, а сирий рядок корисний. |
| `confidence` | Дає дешеву політику: все нижче 0.6 їде в окрему секцію звіту на ручну перевірку. У прогоні туди потрапили саме ті 4 запити, які й людині неочевидні. |
| `is_multi_request` | REQ-010 — це дві задачі в одному повідомленні. Чесніше позначити, ніж тихо злити в один пункт або самовільно розщепити рядок і розʼїхатися з вихідним `id`. |
| `language` | У датасеті є украïнська, суржик і англійська (REQ-006). Поле показує, чи не деградує якість на змішаних текстах. |

**Чого свідомо немає:** поля `duplicate_of`. REQ-013 — це явний дублікат REQ-001
(«той самий звіт, що Оля просила»), але при построковій обробці модель не бачить
решти інбоксу, і будь-яке значення тут було б галюцинацією. Правильне місце для
дедуплікації — окремий прохід після основного циклу (див. «що далі»).

## Де рішення ламається

### Невалідний вивід LLM

Три рубежі, від дешевого до дорогого:

1. **`response_schema` у виклику** — модель фізично не може повернути значення поза
   enum чи зламати структуру. Це знімає більшість проблем ще до парсингу.
2. **Валідація pydantic** — ловить те, що схемою не виражається:
   - `target_department` нормалізується за словником реальних відділів; незнайомий
     відділ → `null`, а не вигадка;
   - `needs_clarification: false` із порожнім `requested_actions` відхиляється
     (крім категорії «поза скоупом»);
   - `needs_clarification: true` без жодного питання відхиляється;
   - `confidence` поза `[0, 1]`, зайві поля, порожній `short_summary`.
3. **Ремонт** — текст помилки валідації йде назад у модель окремим промптом
   («ти повернув X, помилка Y, виправ саме це»). За замовчуванням одна спроба.

Якщо всі спроби вичерпано, запит **не губиться**: він лишається в `output.json`
зі `status: "failed"` і текстом останньої помилки, і окремою секцією у звіті.
Один поганий рядок не валить прогін.

У поточному прогоні через ремонт пройшли REQ-002 і REQ-011 — мок навмисно віддає
на них обрізаний JSON у ```-обгортці та `category: "незрозуміло"` з
`confidence: 1.4`. Обидва полагоджено з другої спроби, це видно в полі `attempts`
і в секції звіту «Вивід LLM довелось лагодити».

**Що лишилось відкритим:** валідна за схемою, але змістовно хибна відповідь.
Якщо модель упевнено віднесе баг до «автоматизації», жодна перевірка це не
зловить. Частково закрито через `confidence` + `priority_rationale` (є на що
дивитись при ревʼю), повністю — ні.

### Великий обсяг

На 18 рядках усе працює за секунду. Що зміниться на умовних 10 000:

- **Rate limits.** Перевірено наживо: безкоштовний тір `gemini-3.6-flash` дає
  лише **5 запитів на хвилину**. На 18 рядках з `--concurrency 5` це одразу дало
  8 із 18 запитів `429 RESOURCE_EXHAUSTED` (лог і цифри — у розділі нижче).
  Закрито наполовину: є семафор (`--concurrency`, для free tier треба `1`) і
  експоненційний backoff з джитером на 429. Але глобального throttling під
  конкретний RPM немає — при `--concurrency` вище ліміту провайдера частина
  запитів все одно впаде з першої хвилі, і врятує їх лише повторний запуск (кеш
  не дасть переплатити за вже готові).
- **Памʼять.** Зараз увесь інбокс і всі результати тримаються в памʼяті, а
  `asyncio.gather` створює корутину на кожен рядок одразу. На десятках тисяч це
  треба переписати на потокову обробку батчами з дозаписом у файл. Не закрито.
- **Відновлення після обриву.** Кеш на диску працює як груба контрольна точка:
  повторний запуск не переплачує за вже оброблені рядки (перевірено — другий
  прогін дає `з кешу=18` і 0.0 с). Але окремого стану «оброблено до рядка N» немає.

### Недетермінізм

`temperature=0` знижує розкид, але **не дає** відтворюваності: той самий вхід у
різні дні може дати іншу категорію на межових запитах (REQ-016 — це баг чи
очікувана поведінка? REQ-001 — це «автоматизація» чи «звіт/аналітика»? обидві
відповіді захищаються). Закрито частково:

- `confidence` виносить межові випадки в окрему секцію звіту;
- умови прогону (провайдер, модель, версія промпту, температура) пишуться в
  `metadata` всередині `output.json` — інакше два різні звіти неможливо порівняти;
- кеш робить повторний прогін на тих самих даних побітово однаковим.

Чого немає: заміру узгодженості (прогнати датасет N разів і порахувати, на яких
рядках категорія «пливе»). Це перше, що варто додати перед продакшеном.

### Вартість токенів

Заміряно на цьому датасеті: системний промпт зі схемою ≈ 1 200 токенів, сам
запит ≈ 80, відповідь ≈ 200. Разом ≈ 1 500 токенів на запит, тобто ≈ 27 тис. на
всі 18 — на безкоштовному тірі Gemini Flash це нуль.

Проблема масштабується погано: системний промпт зі схемою — це ~85% вхідних
токенів, і він відправляється **заново для кожного рядка**. На 10 000 запитів це
близько 13 млн вхідних токенів, з яких ~12 млн — той самий текст. Закрито
частково:

- кеш прибирає повторну оплату при перезапусках (найчастіший сценарій під час
  розробки);
- ключ кешу містить версію промпту й модель, тому правка промпту інвалідує його
  сама.

Не закрито: батчинг кількох запитів в один виклик і context caching на боці
провайдера. Обидва прибрали б основну частину витрат, але ускладнюють ремонт
(при батчі помилка в одному елементі тягне за собою перезапит усього батча).

### Обмеження мок-провайдера

Мок працює **тільки** на цих 18 рядках: він шукає відповідь за характерним
фрагментом тексту. На будь-яких інших даних він чесно падає з `LLMError`, а запит
отримує `status: "failed"` — мовчки видати неправильну відповідь він не може.
Якщо текст підпадає під дві фікстури одразу, мок теж падає: під час розробки саме
така колізія («не горить» зачепилось за маркер від «ГОРИТЬ») тихо підставила
чужу відповідь, тому неоднозначність тепер помилка, а не збіг.

## Опціональні плюси: Google Sheets, Telegram, Docker

Усі три написані й пройдені вручну рядок за рядком, з тестами на все, що можна
перевірити без зовнішніх сервісів. Але ні один не прогнаний по-справжньому — ні
службовим Google-акаунтом, ні реальним Telegram-ботом, ні `docker build`.
Ставлюсь до цього так само, як до Gemini до того, як зʼявився ключ: код
читається правильно, але «має працювати» — не те саме, що «працює», і саме
```response_schema```-баг з Gemini — доказ, що ця різниця не абстрактна.

**Google Sheets** ([`integrations/sheets.py`](src/integrations/sheets.py)).
Через `gspread` + service account: `write_to_google_sheet()` відкриває таблицю
за ID, знаходить або створює аркуш `Triage`, повністю очищає його і перезаписує
всіма 18 (чи скільки їх буде) рядками — навмисно ідемпотентно, щоб повторний
прогін не плодив дублікати. Колонки — ті самі, що в `report.csv`. Юніт-тести
покривають форму рядка (`_row`) і те, що відсутність `gspread` у середовищі дає
чітку `IntegrationError`, а не сирий `ModuleNotFoundError` посеред прогону —
це єдине, що реально перевірити без Google-акаунту. Не перевірено: сама
авторизація через `Credentials.from_service_account_file`, чи `ws.update()` з
такими аргументами дійсно приймається бібліотекою на практиці — сигнатура
`gspread` мінялась між 5-ю і 6-ю версією, і я не можу виключити, що наплутав
щось саме тут, поки не побачу реальний виклик.

**Telegram-дайджест** ([`integrations/telegram.py`](src/integrations/telegram.py)).
Без сторонніх бібліотек — один POST на `api.telegram.org` через stdlib
`urllib`. `build_digest_text()` навмисно винесена окремою чистою функцією без
мережі — саме її й покривають тести (7 штук): метадані прогону, список
high-priority з summary, секція «потребують уточнення», обрізання під ліміт
Telegram у 4096 символів. Не перевірено: сам HTTP-виклик і чи `sendMessage`
приймає таке тіло без `parse_mode` так, як я очікую — це дешево перевірити (один
`curl` з реальним токеном), просто нема під рукою бота.

**Docker** ([`Dockerfile`](Dockerfile)). У цій сесії немає `docker` — ні
бінарника, ні демона, а ставити Docker Desktop чи Colima собі самостійно я не
став: це важка системна зміна, а не крок усередині проєкту. Пройшов Dockerfile
вручну як інтерпретатор: `ROOT = Path(__file__).resolve().parent.parent`
всередині контейнера резолвиться в `/app` (`WORKDIR /app` + `COPY src/
./src/`), тому дефолтні `data/input_requests.csv` і `out/` всередині образу
збігаються з тим, що реально копіюється; `ENTRYPOINT ["python", "-m",
"src.main"]` — той самий виклик, яким я весь час ганяв пайплайн на хості, і він
вимагає саме `-m` (пакетний запуск) через відносні імпорти в `main.py`, що
Dockerfile і робить. Додав `.dockerignore`, якого раніше не було — без нього
`.venv/`, `.git/` і `.env` потрапляли в build context. Єдине, що статичний
рев'ю принципово не ловить: чи `pip install` усіх пакетів з `requirements.txt`
(зокрема `google-genai`) відпрацює всередині `python:3.12-slim` без хвостів на
кшталт відсутнього компілятора для якоїсь транзитивної залежності — для цього
потрібен реальний `docker build`, якого я зробити не можу.

## Перевірка на живому Gemini

Прогнав усі 18 запитів через `--provider gemini` (`gemini-3.6-flash`,
`temperature=0.0`) в окремій сесії з реальним ключем. `out/` у репозиторії
залишено на моці — він відтворюваний і безкоштовний для будь-кого без ключа —
але сама перевірка виявила три реальні проблеми ще до першого валідного рядка.

**1. `response_schema` з pydantic напряму Gemini не приймає.** Перший же
виклик впав з `400 INVALID_ARGUMENT: Unknown name "additional_properties"`.
Pydantic-схема містить `$ref`/`$defs` (винесені enum'и), `additionalProperties`
і `anyOf` для `Optional[...]` — Gemini `response_schema` підтримує урізаний
OpenAPI-підмножина без цього. Мок цю проблему пропустив, бо не ходить в
реальний API і не бачить формату, який той насправді очікує. Виправлено
конвертером [`to_gemini_schema`](src/llm/gemini.py) — резолвить `$ref` inline,
перетворює `anyOf [X, null]` на `{type: X, nullable: true}`, прибирає
непідтримувані ключі.

**2. `gemini-2.0-flash` більше не існує.** Наступна відповідь API:
`404 NOT_FOUND: ... use models/gemini-3.6-flash`. Модель, яку я вибрав під час
розробки (до знань були відомі моделі лише по березень 2026), встигла
депрекейтнутись. Замінено дефолт на `gemini-3.6-flash` в
[`gemini.py`](src/llm/gemini.py) і `.env.example`.

**3. Free tier — 5 запитів на хвилину, не 15, як я вважав.** З цими
виправленнями перший повний прогін (`--concurrency 5`) дав `ok=10 failed=8` —
усі 8 впали з `429 RESOURCE_EXHAUSTED`, і повідомлення прямо назвало ліміт:
`limit: 5, model: gemini-3.6-flash`. Це саме та ситуація, яку мав ловити
backoff — і він таки ловив, просто чотирьох спроб з інтервалами 1-2-4-8с не
вистачає під ліміт 5/хв за одночасних 5 запитів. Запит не загубився (усі 8
лишились у `output.json` зі `status: failed`), а два повторні прогони з
`--concurrency 1` — кеш підхопив уже готові рядки — добили решту до `ok=18
failed=0`. Цифру в README вище виправлено з припущення на заміряну.

Після всіх виправлень — **18/18, 0 помилок**, без жодного ремонту (модель із
першої спроби повертала валідний за схемою JSON на кожному рядку; ремонт
раніше ловив биті відповіді тільки в мок-фікстурах, зроблених навмисно битими).

**Як реальні відповіді розійшлися з моїми фікстурами** — це вже не баг, а
різниця в поведінці моделей:

- **`target_department` живий Gemini визначає значно консервативніше.** У
  моєму мок-прогоні відділ проставлено в 14 із 18 записів (я сам писав
  фікстури і був щедрішим на здогадки — наприклад, поставив «маркетинг» для
  запиту про Google Ads). Жива модель поставила відділ лише в 4 із 18, а
  Google Ads-запит (REQ-001) лишила з `target_department: null`. Це буквально
  виконання інструкції з промпту («тільки якщо явно названий... не вгадуй») —
  просто живий Gemini дотримується її строгіше, ніж я сам, коли вручну писав
  очікувану відповідь.
- **REQ-016** («баг це чи так і має бути») мок відніс до «баг/підтримка», жива
  модель — до «питання/консультація». Обидва варіанти захищаються: автор і
  сам не знає, це прикордонний випадок. Саме для цього в схемі є `confidence`
  — жива модель поставила тут 0.55, нижче порогу 0.6, тобто чесно позначила
  невпевненість замість того, щоб видати категорію з фальшивою певністю.
- Категорії, пріоритети й переліки дій на однозначних запитах (REQ-005, REQ-007,
  REQ-017 — усі три «терміново») збіглися з фікстурами практично дослівно.

## Що зробив би далі

За пріоритетом, а не за списком «плюсів» із ТЗ:

1. **Замір узгодженості.** Прогнати датасет 5 разів і порахувати, на яких рядках
   категорія чи пріоритет пливуть. Без цієї цифри незрозуміло, наскільки взагалі
   можна довіряти виводу — і це важливіше за будь-яку нову інтеграцію.
2. **Розмічений золотий набір.** 18 рядків, розмічених людиною, і accuracy по
   категорії/пріоритету. Тоді правки промпту можна перевіряти, а не вгадувати.
3. **Дедуплікація окремим проходом.** Після основного циклу — один виклик по всіх
   `short_summary` разом (або ембединги + поріг схожості), щоб знайти пари на
   кшталт REQ-001 / REQ-013. Дешево, бо summary короткі.
4. **Розщеплення мультизапитів.** Зараз `is_multi_request` лише позначає проблему.
   Наступний крок — віддавати список підзадач із власними `id` виду `REQ-010.1`.
5. **Context caching + батчинг** — коли обсяг виросте настільки, що вартість
   почне мати значення.
6. **Реально прогнати Google Sheets, Telegram і Docker.** Усі три написані
   (розділ [«Опціональні плюси»](#опціональні-плюси-google-sheets-telegram-docker)),
   але жоден не бачив живого сервіс-акаунта, бота чи `docker build` — перше, що
   зробив би з реальним доступом, а не наступна фіча.
